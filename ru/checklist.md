# Чек-лист готовности к Stage 1 и Stage 2

> Рабочий список того, что аудитор будет смотреть и спрашивать. Чтобы вы не узнавали о пропусках в момент аудита, а заранее.

Этот чек-лист построен по контролям Annex A в редакции 2022 г. Каждый блок содержит 3–5 проверочных вопросов и пример того, как выглядит готовое доказательство для критичных контролей.

Если вы только запускаете проект – начните с [implementation-guide.md](implementation-guide.md). Готовитесь к Stage 2 – держите этот файл под рукой в последние месяцы.

## Готовность на уровне управленческой системы (клаузы 4–10)

Это то, без чего сертификация невозможна в принципе. Проверьте до того, как звать аудитора.

- [ ] **ISMS Scope Statement** (ISMS – Information Security Management System, система менеджмента информационной безопасности) утверждён высшим руководством. Подпись, дата.
- [ ] **Information Security Policy** утверждена высшим руководством.
- [ ] **Risk Assessment Methodology** утверждена. Шкалы, критерии принятия рисков, кто владеет рисками.
- [ ] **Реестр активов** заполнен и согласован. С владельцами и классификацией.
- [ ] **Risk Assessment Report** – минимум один полный цикл оценки.
- [ ] **Statement of Applicability (SoA – положение о применимости)** с обоснованиями включения и исключения каждого контроля.
- [ ] **Risk Treatment Plan (RTP – план обработки рисков)** с владельцами действий, сроками и ресурсами.
- [ ] **Information Security Objectives** – измеримые, с метриками и владельцами.
- [ ] **Программа внутреннего аудита** разработана. Покрытие всех клауз и применимых контролей в цикле.
- [ ] **Минимум один внутренний аудит** проведён независимым аудитором.
- [ ] **Management Review** проведён высшим руководством. Протокол подписан, обязательные входы и выходы зафиксированы.
- [ ] Все NC из внутреннего аудита закрыты или находятся в процессе закрытия с планом.

## A.5 – Organizational controls

### A.5.1 Политики ИБ

- [ ] ISMS Policy утверждена высшим руководством (подпись, дата).
- [ ] График пересмотра не реже раза в год.
- [ ] Тематические политики (доступ, криптография, поставщики, инциденты) утверждены и доступны сотрудникам.

### A.5.7 Threat Intelligence (новый контроль 2022)

- [ ] Кто отвечает за threat intelligence? Документированный процесс?
- [ ] Какие источники фидов используются?
- [ ] Как threat intelligence влияет на риск-реестр и обновление политик?
- [ ] Есть доказательства действий на основе intel за последние 6 месяцев?

**Как выглядит готовое доказательство:** отчёт по threat intelligence за последний квартал плюс минимум 2 примера обновления Risk Treatment Plan или контроля безопасности как реакция на intel.

### A.5.9 Asset Inventory

- [ ] Реестр активов покрывает все типы: оборудование, программное обеспечение, SaaS, информация, люди.
- [ ] Каждому активу присвоен владелец.
- [ ] Классификация чувствительности проставлена.
- [ ] Регулярная сверка с реальностью (минимум раз в полгода).

**Как выглядит готовое доказательство:** экспорт реестра с владельцами и классификацией плюс протокол последней сверки.

### A.5.18 Access Rights

- [ ] Документированный процесс JML (Joiner-Mover-Leaver, приход-перевод-уход)?
- [ ] Периодические пересмотры доступа проводятся? С какой частотой? Кто подписывает?
- [ ] Привилегированный доступ управляется отдельно (см. A.8.2)?

**Как выглядит готовое доказательство:** записи последних пересмотров доступа со списком проверяющих, датой, конкретными исправлениями.

### A.5.19–A.5.23 Supplier Security

- [ ] Реестр поставщиков с уровнями критичности?
- [ ] Контракты содержат ИБ-пункты (защита данных, право на аудит, SLA уведомлений об инцидентах)?
- [ ] Проверка проводится перед привлечением нового поставщика?
- [ ] Облачные сервисы покрыты A.5.23 (требования для облачных сервисов)?

**Как выглядит готовое доказательство:** реестр поставщиков плюс 3 примера подписанных контрактов с ИБ-пунктами плюс отчёт о проверке за последний год.

### A.5.23 Cloud Services (новый контроль 2022)

- [ ] Cloud Security Policy утверждена?
- [ ] По каждому облачному сервису – кто решал использовать и на основе каких критериев?
- [ ] Прописана стратегия выхода в контракте с провайдером?
- [ ] Модель разделения ответственности задокументирована?

**Как выглядит готовое доказательство:** реестр облачных сервисов плюс стратегия выхода для топ-3 критичных провайдеров.

### A.5.24–A.5.27 Incident Management

- [ ] Документированная процедура incident management?
- [ ] Все сотрудники знают, как сообщать об инциденте?
- [ ] Зафиксированные инциденты за последние 12 месяцев? Сколько?
- [ ] Разборы после инцидентов оформляются?

**Как выглядит готовое доказательство:** минимум 1–2 реальных отчёта об инциденте (даже мелких) с разбором уроков за последние 6 месяцев.

«Ноль инцидентов» аудитор трактует как «нет детекции».

### A.5.30 ICT Readiness (новый контроль 2022)

- [ ] ICT Continuity Plan утверждён?
- [ ] RTO и RPO определены по критичным системам?
- [ ] Тесты аварийного восстановления проведены за последние 12 месяцев? Где протоколы?

**Как выглядит готовое доказательство:** протокол последнего DR-теста плюс ICT Continuity Plan плюс BIA (Business Impact Analysis, анализ влияния на бизнес).

### A.5.34 Privacy and Protection of PII

- [ ] Privacy Policy утверждена и опубликована?
- [ ] Регистрация у регулятора (если требуется в вашей юрисдикции)?
- [ ] Процедура обработки запросов субъектов данных?
- [ ] DPIA для высокорисковых обработок?

## A.6 – People controls

### A.6.1 Screening

- [ ] Процедура проверки кандидатов?
- [ ] Уровень проверки соответствует чувствительности роли?
- [ ] Записи скринингов хранятся?

### A.6.3 Awareness

- [ ] Каждый сотрудник проходит вводный инструктаж?
- [ ] Ежегодное повторное обучение для всех?
- [ ] Покрытие включает подрядчиков?
- [ ] Содержание отражает актуальные угрозы (фишинг, AI-риски, ransomware)?

**Как выглядит готовое доказательство:** матрица обучения с покрытием 100% сотрудников плюс примеры материалов.

### A.6.7 Remote Working

- [ ] Remote Work Policy утверждена?
- [ ] Все удалённые устройства управляются через MDM?
- [ ] VPN или Zero Trust настроены для доступа к корпоративным ресурсам?
- [ ] BYOD прописан отдельно (если используется)?

## A.7 – Physical controls

### A.7.4 Physical Security Monitoring (новый контроль 2022)

- [ ] Определены зоны ограниченного доступа?
- [ ] Какие средства мониторинга развёрнуты (CCTV, сигнализация, охрана)?
- [ ] Сроки хранения видеозаписей соответствуют локальному законодательству?
- [ ] DPIA (Data Protection Impact Assessment, оценка воздействия на защиту данных) проведено перед развёртыванием CCTV?

**Как выглядит готовое доказательство:** карта зон плюс конфигурация CCTV плюс DPIA плюс политика хранения.

### A.7.7 Clear Desk и Screen Lock

- [ ] Политика чистого стола и блокировки экрана утверждена?
- [ ] GPO или MDM настроен на автоблокировку?
- [ ] Обходные аудиты проводятся?

Аудитор пройдёт по офису и посмотрит, есть ли незаблокированные ноутбуки, бумаги с PII на столах, стикеры с паролями.

## A.8 – Technological controls

### A.8.8 Vulnerability Management

- [ ] Регулярные сканы уязвимостей проводятся (минимум раз в месяц)?
- [ ] SLA закрытия определён по риск-оценке (CVSS × критичность актива × доступность), а не по плоскому CVSS-скору? ISO 27002:2022 §8.8 требует именно риск-ориентированного приоритета.
- [ ] Доказательства закрытия найденных уязвимостей хранятся?
- [ ] Управление патчами покрывает унаследованные системы (если есть)?

**Как выглядит готовое доказательство:** отчёт скана плюс тикеты по устранению с датами закрытия.

### A.8.9 Configuration Management (новый контроль 2022)

- [ ] Hardening baselines (CIS Benchmarks, STIG) утверждены?
- [ ] Конфигурации применяются автоматически (через IaC)?
- [ ] Дрейф конфигураций мониторится?
- [ ] Изменения логируются?

### A.8.10 Information Deletion (новый контроль 2022)

- [ ] Расписание хранения данных утверждено?
- [ ] Процедуры безопасного удаления покрывают все типы носителей (HDD, SSD, облако)?
- [ ] Бэкапы включены в политику хранения и удаления?
- [ ] Доказательства обработки запросов на удаление по GDPR, закону РК 94-V хранятся?

### A.8.11 Data Masking (новый контроль 2022)

- [ ] Продовые PII в непродовых средах маскируются?
- [ ] Инструменты маскирования настроены?
- [ ] Дев-команды знают, как использовать маскированные наборы данных?

### A.8.12 Data Leakage Prevention (новый контроль 2022)

- [ ] DLP развёрнут на конечных устройствах, в почте, в вебе?
- [ ] Классификация данных настроена в инструментах?
- [ ] Инциденты DLP за последние 6 месяцев есть в логах?
- [ ] Процесс реакции на DLP-оповещения работает?

**Как выглядит готовое доказательство:** список DLP-инцидентов с классификацией плюс протоколы реакции.

### A.8.13 Backup

- [ ] Backup Policy утверждена?
- [ ] Тесты восстановления проводятся (минимум раз в полгода)?
- [ ] Записи о тестах восстановления хранятся?

**Как выглядит готовое доказательство:** протоколы 2–3 последних тестов восстановления с датами и результатами.

### A.8.15 + A.8.16 Logging и Monitoring (последний – новый контроль 2022)

- [ ] Централизованное логирование настроено?
- [ ] Сроки хранения логов соответствуют политике?
- [ ] SIEM с рабочими сценариями работает?
- [ ] Доказательства реакции на оповещения за последние 6 месяцев?

**Как выглядит готовое доказательство:** 2–3 закрытых тикета по инцидентам из SIEM-оповещений с таймлайном и разбором уроков.

### A.8.23 Web Filtering (новый контроль 2022)

- [ ] Web Filtering работает в офисе и для удалённых пользователей (VPN, SASE)?
- [ ] Категории запрещённых сайтов утверждены?
- [ ] AI-сервисы (ChatGPT и прочие) – политика определена (разрешить, запретить, условно)?
- [ ] Периодический пересмотр категорий проводится?

### A.8.24 Cryptography

- [ ] Cryptography Policy утверждена?
- [ ] Жизненный цикл управления ключами определён (генерация, ротация, отзыв, архив)?
- [ ] Секреты не лежат в открытом виде в Git, CI, Wiki?
- [ ] TLS-сертификаты обновляются автоматически?

### A.8.28 Secure Coding (новый контроль 2022)

- [ ] Стандарты безопасной разработки утверждены?
- [ ] Обязательный код-ревью для всех PR в прод?
- [ ] SAST и DAST в CI/CD-пайплайне?
- [ ] SBoM и SCA для сторонних библиотек ведутся?

**Как выглядит готовое доказательство:** логи git с подтверждениями код-ревью плюс последний SAST-отчёт плюс SBoM для главного продукта.

### A.8.32 Change Management

- [ ] Процедура управления изменениями утверждена?
- [ ] CAB или эквивалент собирается с заданной частотой?
- [ ] Процесс экстренного изменения определён?

## Когда чек-лист завершён

Прошли его честно и закрыли все пункты – вы готовы к Stage 1. Stage 2 пройдёт спокойнее, чем кажется.

Остались красные пункты? Для каждого определите:

1. Это блокер или второстепенное?
2. Сколько времени и денег нужно, чтобы закрыть?
3. Можно ли договориться с CB (Certification Body, орган по сертификации) о небольшой отсрочке через изменение области сертификации?

Стресс перед аудитом нормален. Не паникуйте, а методично закрывайте позиции.
